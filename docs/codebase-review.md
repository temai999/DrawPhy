# DrawPhy 代码库评审报告

> 评审日期：2026-11-05 · 基线：阶段 4 完成（13/16 类型已模块化，逻辑自检 83 项、交互自检 47 项全绿）
> 评审维度：架构结构 / 实现方式 / UI 交互 / 业务能力
> 严重度标记：🔴 阻断级（不修会出事故）· 🟡 高危（持续失血）· 🟢 中低（技术债）

---

## 一、总体结论

DrawPhy 是一个**约束驱动设计做得相当克制**的项目：零依赖、零构建、file:// 直开，这三条硬约束逼出了 IIFE + 全局命名空间 + script 顺序加载的合理方案，并且用「registry 双轨分派」把模块化迁移的风险压到了接近零。截至阶段 4，13 个图元类型已迁为独立模块，自检网 83+47 项全绿，迁移过程没有破坏任何旧行为——这在没有版本控制的情况下完成，值得肯定。

但代码库同时存在**三个结构性隐患**：单文件巨石（ui.js 2353 行）、双轨分派的永久漂移风险、以及全量快照历史在大文档下的性能天花板。这三者决定了路线图（见 `roadmap.md`）的排序。

### 2.2 设计决策的合理性（保留项）

以下决策**经过验证是正确的，评审不推翻**，后续开发必须遵守：

1. **放弃 ES module 改 IIFE + `DP` 命名空间**：file:// 下 ES module 被 CORS 阻断，这是唯一可行解。所有模块文件以 `(function () { 'use strict'; DP.defineModule('type', function (DP) { ... }); })();` 包裹。
2. **双轨分派**（registry 有模块优先、否则旧 switch）：使 13 次迁移零事故，任何模块加载失败页面仍可运行。这是项目最重要的安全资产。
3. **扁平对象数组 + 按 type 分派**：`DP.state.objects` 无场景树。对教学绘图这个规模（百级对象）足够，不值得为它引入图层树复杂度。
4. **单一渲染器三处复用**：`render.js` 同时服务画布、部件缩略图、PNG/SVG 导出，保证所见即所得。
5. **`bind = {x1:{id,dx,dy}}` 相对偏移绑定**：宿主缩放时导线自动跟随，偏移存相对宿主包围盒中心，数据可序列化。

### 2.3 结构性问题清单

**🔴 问题 1：无版本控制**
项目没有 git，回退全靠 `backup/` 下手工快照（pre-modular / pre-p0 / pre-stage2 / pre-stage3 / pre-stage4）。快照粒度粗、与业务演进无关联，且人工操作必然遗漏。**这是全库最高优先级的债**：一次误删或误改即可能丢失数周工作。
→ 处置：`git init` + 首提交 + `.gitignore`（排除 `backup/`、`_check/*.png`），路线图第 0 阶段。

**🟡 问题 2：双轨分派的漂移面在扩大**
双轨的安全代价是「同一行为存在两处实现」。已经发生两类漂移：
- `R.primitive`（部件内部图元渲染）仍走旧 switch，registry 管不到部件内部 → 顶层对象模块化 ≠ 全部模块化；
- textbox/callout 的**创建**仍在 `ui.js` 内联构造，没走模块 `defaults()` 工厂（rect/arrow 走工厂），构造路径两套。
迁移期这是可接受的，但每多迁一个类型，漂移面就大一分。路线图阶段 5 末必须做一次「旧 switch 摘除」收尾，让双轨收敛为单轨 + 模块缺失兜底。
→ 规则（写入开发指南）：**迁移一个类型时，创建/命中/变换/渲染四条路径必须全部改走 registry，缺一不可**。

**🟡 问题 3：registry 三表只用两表**
`registry.registerPart()` / `getPart()` 自阶段 1 起零调用方，114 个部件仍由 `parts.js` 的 `DP.parts.byId` 独立维护。存在两套「部件定义」口径，未来加部件端子/参数化属性时必然踩坑。
→ 处置：阶段 5 部件数据化时统一走 registry，`DP.parts.byId` 改为 `registry.getPart` 的薄包装（保持旧 API 兼容）。

**🟡 问题 4：ui.js 巨石化**
2353 行 / 57 个顶层函数，五种职责（工具构建、指针事件、命中与节点、文本编辑、属性面板与剪贴板分组）挤在一个 IIFE 里。`onDown` 单个函数约 320 行，内含 23 个工具的分支。**当前还能工作是因为事件流程是线性的，但一旦加新交互模式（如旋转手柄、多选框选外的套索），改动成本会指数上升。**
→ 处置：阶段 6 命令式历史重构时，顺手把 ui.js 按职责切成 4 个文件（`ui/tools.js`、`ui/pointer.js`、`ui/text-edit.js`、`ui/panels.js`），全部挂到 `DP.ui` 下，行为不变。

**🟢 问题 5：script 顺序无校验**
`index.html` 23 个 script 顺序硬编码，若有人在 core.js 之前加载模块，`DP.defineModule` 不存在会直接抛错、白屏。`_check/test.html` 已能间接发现（模块注册断言失败），可接受，暂不处理。

**🟢 问题 6：eventbus 死代码**
`DP.bus` 已就绪但零订阅。不是浪费 33 行的问题，而是「阶段 7 命令式历史」的信号基建已经预置。阶段 6 直接启用，不必重写。

## 三、实现方式评审

### 3.1 数据模型

- **文档格式**：`{version:1, page, objects[], groups{}}`，纯 JSON 可序列化，文件可逆。良好。
- **对象模型**：每个对象扁平字典 + `type` 字段 + 自有几何字段（rect 用 `x,y,w,h`；line 用 `x1,y1,x2,y2`；arc 用 `cx,cy,r,a0,a1`）。字段命名不统一是历史包袱，但已在各模块内部消化，**不要试图统一字段命名**（会破坏全部存量 JSON）。
- **深拷贝**：`M.clone = JSON.parse(JSON.stringify(v))`。对纯数据对象安全；若未来对象里塞函数/Date/undefined 会静默丢失——已写入开发指南禁止事项。
- **分组**：`o.group = groupId`，`groups` 表只记存在性。够用。

### 3.2 历史（撤销/重做）——当前最大的实现天花板 🔴

```js
H.snapshot() → JSON.stringify({objects, groups})   // 每次操作全量序列化
H.push()     → 存入栈，上限 80 步
```

问题：
1. **O(n) 全量快照**：每次 push 都把整个文档 stringify 一遍。百对象文档尚可（实测无感），但 80 步栈 × 全量字符串的内存占用随对象数线性膨胀，且大文档下每步操作的卡顿会线性增长。
2. **快照去重只比对栈顶字符串**：`if (this.stack[this.idx] === s) return`，同值不同引用场景下字符串相等即跳过——逻辑正确，但意味着每次 push 都要先做一次完整 stringify 才能判断「是否值得入栈」。
3. **dirty 语义**：`push()` 内设 `DP.state.dirty = true`，但纯查看类操作（选中）不该置脏——目前靠调用方控制 push 时机，约定隐晦。

→ 处置：**阶段 6 命令式历史**。命令对象 `{label, do(), undo()}` + eventbus 广播，栈里只存命令不存状态，undo/redo 回放命令。这是 EE 类编辑器的标准方案，同时彻底解决内存与卡顿。eventbus 就是为此预置的。80 步上限在命令式下可放宽到 200（命令几乎不占内存）。

### 3.3 渲染

- **字符串拼接 innerHTML**：`overlaySvg()` 每次全量重建 SVG。对象数百时重绘耗时主要在字符串拼装，实测当前规模无感；但缺少脏矩形/分层，任何小改动都全量重绘。
- **无空间索引**：`hitTest` 顺序遍历 `objects` 逐个调模块 `hitTest`，O(n)。百级对象无感，千级会卡。
- **坐标系**：`DP.state.view = {x, y, k}` 单一缩放因子（无独立 xy 缩放），`toWorld` 一处换算。良好。
→ 处置：阶段 6 顺手做「按 bbox 粗筛 + 模块精测」的两段命中（粗筛逻辑在 model 层，模块无感知）；分层渲染推到阶段 8 视需要再做，**现在不做**。

### 3.4 吸附引擎（亮点，保持不动）

`S.resolve(p, ctx)` 单入口，内部按优先级：交点 → 端点/中点/圆心/象限 → 正交磁吸 → 栅格，Shift 强制 15° 角度约束。吸附点收集 `S.collectPoints` 与几何求交 `S.intersections` 分离，扩展新图元只需在模块 `anchors()` 里返回正确 `kind`，**无需碰吸附引擎**。这是模块化红利已经兑现的部分，评审结论：冻结，不改。

### 3.5 函数图像（func.js）

`DP.compileFunc(expr)` 把用户表达式 `new Function` 化后逐点求值。无沙箱、无超时。教学工具、本地运行、表达式来自用户自己输入——风险等级低，但**写入开发指南：不得把 compileFunc 用于任何对外/多用户场景**。

### 4.2 交互一致性

- 吸附提示、光标形态（crosshair/ move / handle）、Shift/Ctrl/Alt 修饰键语义在全部工具上已统一，回归网锁住了行为。
- 部件库 114 项 11 类经缩略图渲染与画布同一渲染器，所见即所得。
- **缺口（业务能力向）**：部件没有命名端子——把导线粘到「电池正极」目前靠几何端点吸附，体验达标但语义缺失（导线不知道自己在正极还是负极）。这是阶段 5 命名端子要解决的，也是模块化数据化的主要业务动机。
